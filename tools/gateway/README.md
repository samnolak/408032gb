# tools/gateway — тонкий OpenAI-совместимый шлюз перед движком

Один файл `gateway.py`, только стандартная библиотека Python 3 (на VM нет интернета, pip не нужен).
Шлюз стоит перед **одним** однопоточным движком (кандидаты: llama.cpp `llama-server`, ik_llama.cpp,
Strata `serve`, ExLlamaV3/TabbyAPI; движок не выбран) и добавляет то, что от движка не требуем:
аутентификацию, очередь с ограничением, обрыв генерации при уходе клиента, проверку длины контекста,
журнал запросов и метрики. Шлюз не знает ничего о конкретном движке, кроме двух диалектов `/tokenize`.

## Запуск

```
python3 tools/gateway/gateway.py --listen 127.0.0.1:8000 --backend http://127.0.0.1:8080 \
    --api-keys-file /etc/gateway/keys --max-concurrency 1 --max-queue 8 \
    --max-context-tokens 262144 --set-default cache_prompt=true \
    --log-file /var/log/gateway/requests.jsonl
```

## Эндпоинты

| путь | что делает | auth | очередь |
|---|---|---|---|
| `POST /v1/chat/completions`, `POST /v1/completions` | проксирует; SSE передаётся кусками по мере прихода, без накопления | да | да |
| `GET /v1/models`, `POST /tokenize`, `POST /detokenize` | проксирует как есть | да | нет |
| `GET /health` | JSON: состояние шлюза и доступность `GET /health` движка; 200 только если движок ответил 200 и шлюз не в drain, иначе 503 | нет | нет |
| `GET /metrics` | Prometheus text: запросы по пути и коду, in-flight, длина очереди, отказы 429, ошибки движка по видам, уходы клиентов по фазам, исходы проверки контекста, summary TTFT / полной длительности / ожидания в очереди | нет | нет |

`/health` и `/metrics` не требуют ключа (как `/health` у llama-server) и не пишутся в JSONL-журнал.

## Флаги

| флаг | по умолчанию | смысл |
|---|---|---|
| `--listen HOST:PORT` | `127.0.0.1:8000` | где слушать; порт 0 — любой свободный |
| `--backend URL` | обязателен | базовый URL движка (`/v1` в конце допускается) |
| `--api-keys-file` | нет | ключи Bearer, по одному на строку, `#` — комментарий. Без файла auth выключен и при старте пишется WARNING. Файл без ключей — отказ запуска. Значения ключей не пишутся никуда, только их число |
| `--backend-api-key-file` | нет | ключ, который шлюз сам отправляет движку (ключ клиента дальше шлюза не уходит) |
| `--max-concurrency N` | 1 | сколько генераций одновременно у движка |
| `--max-queue M` | 8 | сколько ждут; при полной очереди 429 + `Retry-After` + ошибка в формате OpenAI (`rate_limit_error` / `queue_full`). Очередь строго FIFO |
| `--retry-after-s` | 5 | значение `Retry-After` (фиксированное, не оценка) |
| `--max-context-tokens T` | выкл. | отказ 400 (`context_length_exceeded`) если токены промпта + `max_tokens` > T, до того как запрос попадёт к движку |
| `--tokenize-dialect` | `auto` | `auto`/`llamacpp`/`vllm`/`off` — как считать токены |
| `--set-default KEY=JSON` | нет | добавить ключ в тело генерации, только если клиент его не прислал (повторяемый). Пример: `cache_prompt=true` для llama.cpp |
| `--log-file` | нет | JSONL-журнал, по строке на запрос (`-` = stdout) |
| `--log-prompts` | выкл. | писать в журнал текст промпта / messages (по умолчанию не пишется) |
| `--connect-timeout-s` | 5 | таймаут соединения с движком |
| `--backend-timeout-s` | 3600 | таймаут одного блокирующего чтения от движка; должен быть больше самого долгого prefill (для не-потоковых запросов — всей генерации) |
| `--guard-timeout-s` | 30 | таймаут `/tokenize`, `/apply-template`, проксирования `/v1/models` |
| `--drain-s` | 30 | при SIGTERM/SIGINT: перестать принимать соединения и ждать завершения начатых и стоящих в очереди запросов не дольше этого; код выхода 0, если успели, иначе 1 |
| `--max-body-mb` | 64 | предел размера тела запроса (413) |
| `--verbose` | выкл. | отладочный журнал в stderr |

## Поведение

**Тело запроса не меняется.** Байты от клиента уходят движку как есть (порядок ключей, пробелы,
экранирование): префиксный кэш движка видит тот же промпт, что и без шлюза. Единственное исключение —
`--set-default`: пара `"key":value` вставляется текстом перед закрывающей `}` и только если ключа нет.

**Очередь и уход клиента.** До `--max-concurrency` запросов у движка, до `--max-queue` ждут по FIFO.
Отдельный поток следит за сокетом клиента (`recv(MSG_PEEK)` вернул пусто = клиент закрыл соединение):
- клиент ушёл, пока ждал в очереди — запрос удаляется из очереди и до движка не доходит (в журнале 499);
- клиент ушёл, пока движок думает (prefill, ни одного байта ещё нет) или пока идёт поток — шлюз
  закрывает TCP-соединение с движком. У llama-server закрытие соединения останавливает задачу:
  `should_stop` = `is_connection_closed` из httplib (`tools/server/server-http.cpp:736@ec7630a`),
  проверяется и в потоковом (`tools/server/server-context.cpp:4426`), и в обычном ответе
  (`:4352@ec7630a`). Это **PROVISIONAL** (чтение кода, на живом движке NOT RUN). Для остальных
  движков — **UNKNOWN**.

**Проверка контекста** (`--max-context-tokens`). Токены считает сам движок, шлюз ничего не оценивает:
- llama.cpp / ik_llama.cpp: `POST /tokenize {"content": text, "add_special": true}` → `{"tokens": [...]}`;
  для chat сначала `POST /apply-template` с тем же телом → `{"prompt": text}`. Эндпоинты есть в
  llama.cpp `tools/server/server.cpp:281,283@ec7630a` (**CONFIRMED**) и в ik_llama.cpp
  `examples/server/server.cpp:2256,2258` (**CONFIRMED** в локальном клоне @5194a9e, этого upstream нет
  в таблице пинов). `add_special=true` — как сам llama-server токенизирует промпт генерации
  (`tools/server/server-context.cpp:4299@ec7630a`, **CONFIRMED**);
- vLLM-диалект: `POST /tokenize {"model", "prompt"}` или `{"model", "messages"}` → `{"count": n}`;
- диалект определяется пробой, как в `tools/bench/oa_client.py` (пустой список токенов = промах);
  неудачная проба повторяется не чаще раза в 60 с.
Если считать нечем (нет `/tokenize`, нет `/apply-template` для chat, промпт не строка, ошибка) —
запрос **пропускается** и учитывается в `gateway_context_guard_total{result="unchecked",reason=...}` и
в поле `guard` журнала. Если клиент не указал `max_tokens`/`max_completion_tokens`/`n_predict`,
проверяется только длина промпта (`reason="no_max_tokens"`).

**Ошибки движка.**
- нет соединения → 502 `backend_unreachable`; таймаут до ответа → 504; соединение закрыто до
  ответа → 502; 5xx до первого байта → 502 `backend_error` (503 от движка → 503
  `backend_unavailable`); 4xx движка отдаются клиенту как есть.
- обрыв потока посередине → клиенту уходят все полученные события, затем
  `data: {"error": {..., "code": "backend_truncated"}}` и закрытие соединения. Поддельного
  `data: [DONE]` нет. Формат совпадает с тем, как llama-server сам сообщает об ошибке в потоке
  (`format_oai_sse(json {{ "error", ... }})`, `tools/server/server-context.cpp:4422@ec7630a`).
- **Автоматических повторов нет.** Генерация не идемпотентна: повтор после того, как движок принял
  запрос, заново делает prefill (на 262K контекста у однопоточного движка это минуты) и занимает
  единственный слот; в потоке клиент уже получил часть байтов, и повтор склеил бы два разных ответа.
  Решение о повторе остаётся за клиентом, который видит 502/503/504 или событие ошибки.

**Журнал** (`--log-file`), одна JSON-строка на запрос: `ts`, `id` (тот же, что в заголовке ответа
`X-Request-Id`; генерируется шлюзом), `method`, `path`, `model`, `stream`, `prompt_chars`, `status`,
`queue_s`, `first_byte_s` (заголовки ответа движка), `ttft_s` (первое SSE-событие с генерируемым
содержимым; только для потоков, иначе null), `total_s`, `prompt_tokens`, `completion_tokens`,
`cached_tokens` (из `usage.prompt_tokens_details.cached_tokens` или llama.cpp `timings.cache_n`),
`usage_src` (`usage`/`timings`/null), `guard`, `injected_defaults`, `client_disconnected`, `error`.
Все времена отсчитываются от приёма запроса шлюзом (включая очередь). Текста промпта нет, пока не
указан `--log-prompts`. Строка пишется после последнего байта ответа.

## Ограничения

- Один движок. Маршрутизация по нескольким движкам/моделям — будущая работа.
- TLS не терминирует: слушать на localhost или ставить за nginx/caddy.
- Тела запросов с `Transfer-Encoding: chunked` не принимаются (411); нужен `Content-Length`.
- Ключи читаются при старте; для смены — перезапуск.
- `X-Request-Id` клиента не используется, шлюз всегда выдаёт свой.
- Клиент, который после отправки запроса делает half-close (`shutdown(SHUT_WR)`), выглядит как ушедший
  и получит обрыв. Обычные HTTP-клиенты так не делают.
- На каждый запрос — новое соединение с движком (без пула): закрыть именно его — способ остановить
  генерацию.
- Квантили в summary считаются по скользящему окну последних 2048 значений; `_sum`/`_count` — за всё время.
- Счётчики запросов и строка журнала обновляются после последнего байта ответа: запрос к `/metrics`
  сразу после ответа может ещё не увидеть его.

## Пример unit-файла systemd (не устанавливается)

```ini
[Unit]
Description=OpenAI-compatible gateway in front of the inference engine
After=network-online.target llama-server.service
Wants=network-online.target

[Service]
Type=simple
User=gateway
ExecStart=/usr/bin/python3 /opt/408032gb/tools/gateway/gateway.py \
    --listen 0.0.0.0:8000 --backend http://127.0.0.1:8080 \
    --api-keys-file /etc/gateway/keys \
    --max-concurrency 1 --max-queue 8 --max-context-tokens 262144 \
    --set-default cache_prompt=true \
    --log-file /var/log/gateway/requests.jsonl --drain-s 60
# SIGTERM -> stop accepting, drain up to --drain-s; give systemd a bit more than that
KillSignal=SIGTERM
TimeoutStopSec=75
Restart=on-failure
RestartSec=2
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/log/gateway
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```
