# R2.2 — оценочный набор заказчика: что собрать, в каком формате, что проверяется автоматически

Зачем: публичные индексы (Artificial Analysis и др.) различают кандидатов на 2–4 пункта и противоречат друг другу между
версиями (research/R1 §2.2). Выбор модели и кванта (ADR-013) делается на **задачах заказчика**, в 4 битах, на 32K–262K.
Набор прогоняется на всех кандидатах одним стендом — `tools/eval/` (задача N3 трека без железа; описание формата и
команд — `tools/eval/README.md`).

**Состояние стенда (2026-10-10).** Стенд готов и проверен только на скриптовом мок-сервере: 34 теста, мутационная проверка
16/16 — CONFIRMED, литеральный вывод в `docs/evidence/2026-10-10-eval-stand.md` (коммит `d52d379`). Против реальных движков —
NOT RUN. Задач заказчика пока нет; 15 задач в `tools/eval/tasks-synthetic/` — SYNTHETIC-шаблоны, не доказательство качества.

## Состав (минимум 60 задач; лучше 100)
| часть | категория стенда | сколько | что это | проверка |
|---|---|---|---|---|
| A. code-агент | `code_fix`, `code_write` | 20–40 | реальные задачи из репозиториев заказчика: «исправь баг / добавь функцию», маленький снапшот репозитория + команда тестов | автоматически: ответ применяется к копии, тесты в песочнице, PASS = код возврата 0 |
| B. длинные документы | `long_doc_qa` | 15–30 | документы/кодовые базы 32K–262K токенов + вопросы с однозначным ответом (факт из середины, сравнение двух мест, вычисление по таблице, действующее значение против устаревшего) | автоматически: точное / нормализованное / regex / числовое совпадение |
| C. tool calling | `tool_use` | 10–20 | сценарии с 2–5 инструментами (JSON-схемы), многоходовые, с ответами инструментов | автоматически: обязательные и запрещённые вызовы, аргументы, порядок, лимит ходов, итоговый ответ |
| E. структурированный вывод | `structured_output` | 5–15 | извлечение в JSON по схеме (счета, заявки, классификация) | автоматически: подмножество JSON Schema + значения по JSON Pointer |
| D. рассуждение / чат | `reasoning` (однозначный ответ) + ручная часть | 10–20 | типичные вопросы пользователей заказчика | с однозначным ответом — автоматически; открытые — рубрика 0–2 от людей вслепую, вне стенда |

## Как заказчик передаёт задачи
Два пути, можно смешивать:
1. **Готовые файлы задач.** Одна задача — один файл `*.task.json` по формату `tools/eval/README.md` (раздел 3); образцы
   всех категорий — `tools/eval/tasks-synthetic/` (копировать и менять). Фикстуры (мини-репозитории), документы и скрытые
   тесты кладутся рядом, пути относительные. Желательно `reference_answer` — эталонный ответ, по нему стенд проверяет
   саму задачу.
2. **Материалы, из которых parity-qa собирает задачи** (заказчик потом проверяет):
   - A: снапшот репозитория (или его урезанная часть, которая собирается и тестируется без сети), формулировка задачи,
     команда тестов, которая падает до исправления и проходит после; эталонный патч, если есть;
   - B: документ (текст UTF-8) и вопросы с допустимыми ответами и местом в документе, где ответ;
   - C: схемы инструментов, что каждый инструмент должен вернуть на какие аргументы, какие вызовы обязательны / запрещены,
     важен ли порядок, что должно быть в итоговом ответе;
   - E: входной документ, JSON-схема результата, ожидаемые значения ключевых полей;
   - D: вопросы с однозначным ответом — как B; открытые вопросы — список для ручной оценки.

Доставка: архив каталога набора через ПК заказчика на сервер (интернета на VM нет). Перед прогоном моделей набор
проверяется без сервера: `python3 tools/eval/run_eval.py --tasks <DIR> --validate-only` — формат, пути, эталонные
ответы проходят, нетронутые фикстуры падают, у симулятора есть ответы на обязательные вызовы. Задача с замечанием не
прогоняется, пока её не исправят.

Конфиденциальность (PROVISIONAL — предложение parity-qa, решают lead-architect и заказчик): задачи заказчика и полные
каталоги прогонов (`raw.jsonl`, `results.jsonl` содержат тексты задач и ответы) в публичный репозиторий не кладутся и
хранятся у заказчика. В `docs/evidence/` попадают `meta.json`, `summary.json`/`summary.md` и вывод `compare.py`; хэш набора
(`meta.eval.task_set_sha256`) и хэши задач связывают их с полными каталогами.

## Что проверяется автоматически, а что вручную
| что | автоматически (стенд) | вручную |
|---|---|---|
| формат и целостность набора | `--validate-only`: поля, пути внутри набора, схемы, эталоны, падение нетронутых фикстур | составить задачи; убедиться, что ответ однозначен и тест проверяет именно задачу |
| код (A) | применение FILE-блоков / unified diff к копии, защита тестов от правки, тесты в песочнице (без сети, запись только во временный каталог, лимиты, таймаут) | разбор провалов: модель неправа или задача/тест неоднозначны |
| документы (B), рассуждение (D, однозначные) | извлечение строки `ANSWER:`, сравнение; рассуждение (`reasoning_content`, `<think>`) не оценивается | — |
| инструменты (C) | цикл вызовов через детерминированный симулятор, подпроверки, лимит ходов | — |
| JSON (E) | разбор, схема, значения | — |
| качество текста, стиль, полнота, открытые вопросы (D) | нет | рубрика 0–2 вслепую (без имени модели и кванта), два оценщика |
| вывод для ADR-013 | доли по категориям с интервалом Уилсона 95%; попарно — тест Мак-Немара и бутстреп-интервал разности (`compare.py`) | решение lead-architect с учётом скорости (R1) и ручной части |

Ошибки запросов (сеть, HTTP, оборванный поток) и ошибки стенда считаются отдельно и не входят в долю решённых
(`summary.json`: `n_request_errors`, `n_harness_errors`). Прогон, где их больше нуля, повторяется для этих задач, прежде чем
сравнивать кандидатов.

## Правила
- Задачи не публикуются и не попадают в обучающие данные (локальный сервер).
- Одинаковые промпты, температура 0 (и отдельный прогон с рекомендованными вендором параметрами сэмплинга), одинаковый шаблон
  чата модели, одинаковый `--max-tokens`; режим рассуждения (`--extra-body`) и его бюджет фиксируются и пишутся в `meta.json`.
- Каждая модель × квант × движок прогоняется полностью, `--repeats 3`; результат — доля по категориям и в целом
  на уровне задач (повторы сворачиваются большинством) с интервалом Уилсона.
- Разница между двумя кандидатами учитывается в ADR-013, только если её показывает `compare.py` на одном и том же наборе
  (одинаковые хэши задач): p Мак-Немара < 0.05 и бутстреп-интервал разности не содержит 0. При малом числе несогласованных
  задач (b + c < 6) тест значимости не достигает — это «нет различия на этом наборе», а не «равны».
  Порог 0.05 — PROVISIONAL (предложение parity-qa; утверждает lead-architect).

## Ограничения стенда (подробно — `tools/eval/README.md`, раздел 7)
- Code-задачи — однократный ответ (модель видит файлы в промпте и отвечает патчем). Интерактивный агент, который сам читает
  файлы и запускает тесты через инструменты, этим форматом не моделируется; такая категория — возможное расширение, не сделано.
- Длинные документы на 32K–262K поддерживаются форматом, но стенд на таких длинах не запускался — NOT RUN.
- Песочница проверена на машине разработки (root, ядро 6.18); на сервере заказчика доступность `unshare` и Landlock — UNKNOWN
  до первого `--validate-only`. Без них code-задачи дают `harness_error`, а не провал модели (или `--weak-sandbox` с записью).

## Что нужно от заказчика
Материалы для частей A–C и E (репозитории/документы, которые можно использовать) или разрешение собрать их из его реальных
сессий code-агента; список типичных вопросов для части D; два человека для ручной рубрики части D.
