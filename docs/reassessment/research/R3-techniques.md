## 0.1. Главное в десяти строках

1. **Потолок одного GPU.** При разбиении по слоям (pipeline) и batch 1 в каждый момент работает одна карта, и декод
   ограничен полосой одной 4080 Super. Для 18B активных при 4.5 bpw это ≤70 tok/s в пике и ~54–56 tok/s при КПД 0.8 даже
   при 100% попаданий в VRAM; для реального `UD-Q4_K_XL` (плотная часть ~8.4 ГБ) — ~42 tok/s (HYPOTHESIS, §9).
   **Для `UD-Q4_K_XL` пол 50 tok/s без TP/EP или спекуляции физически недостижим; для «чистых» 4.5 bpw — на грани
   (53–58 tok/s только при h≥0.8 и 8 каналах DDR4)** (HYPOTHESIS, вывод в §9).
2. Поэтому решающие эксперименты — **латентность all-reduce/P2P внутри VM** (будет ли работать TP для плотной части) и
   **кривая попаданий** реальной маршрутизации GLM при ~65–70% экспертов в VRAM (§10, E3–E5).
3. CPU выгоднее считать промахи, чем гнать эксперт по PCIe: 13.5 MiB по PCIe ≈0.59 мс против 0.09–0.17 мс чтения из DDR4;
   PCIe окупается только с ~9–18 токенов на эксперт, т. е. в префилле (HYPOTHESIS, §1.8; согласуется с порогом
   `GGML_OP_OFFLOAD_MIN_BATCH=32` в llama.cpp — VERIFIED).
4. **Число каналов DDR4 (4 или 8) — главный неизвестный параметр CPU-яруса**: оно в 2 раза меняет время промахов.
   Модель CPU «EPYC 7H43» в открытых источниках не найдена (UNKNOWN).
5. Спекуляция на MoE с выгрузкой выигрывает меньше, чем на плотных моделях: окно из k токенов трогает почти k×8 разных
   экспертов. Для GLM при всех экспертах в VRAM MTP с окном 4 даёт ×1.2–1.6, DFlash2 с окном 8 — ×0.96–1.1 при
   независимой маршрутизации (HYPOTHESIS, §8.5); реальное перекрытие экспертов соседних токенов надо посчитать по трассам G0.
6. Лучший доступный аналог нашей машины уже измерен: Strata на EPYC 7453 (Zen 3, AVX2, KVM-гость, PCIe 4.0 ~23–26 GB/s)
   + 2×3090 даёт 93→67 tok/s от 1K до 262K на Qwen3.8-Flash-Next IQ3_XXS (VERIFIED как отчёт в репо Strata; REPORTED как
   замер). Но у той модели плотная часть ~3.5 ГБ против ~8–9 ГБ у GLM-5.3-Flash.
7. KTransformers уже поддерживает GLM-5.3-Flash на SM89 и TP=4, но CPU-ядро для него — AVX-512 FP8 и нужно ≥350 ГБ RAM:
   на нашем сервере как есть не запускается (VERIFIED по документации, §4.1).
8. Engram у DeepSeek-V4.1-Flash: 48 строк × 264 Б = 12.4 КиБ полезных данных на токен, адреса известны до прохода слоя
   (VERIFIED по коду); SSD-ярус с O_DIRECT 4 КиБ + кэш строк в DRAM выглядит выполнимым (HYPOTHESIS, §6).
9. Префиксный кэш для KDA-слоёв решается снимками состояния на границах (vLLM `align`, SGLang `MambaCheckpointPool` с int8,
   LMCache для Kimi-Linear, llama.cpp `--ctx-checkpoints`) — VERIFIED по коду/докам; снимок GLM ≈136 MiB fp32 (HYPOTHESIS).
10. FP8-внимание (а не только FP8-хранение KV) на 128K однажды обвалило NIAH 91%→13% на Hopper до исправления
    накопления (REPORTED); хранить KV в 8 битах, накапливать в fp32.

## 1. MoE: выгрузка и кэширование экспертов

Геометрия, от которой считаем (VERIFIED, `docs/models/glm-5.3-flash.md:7-16@eb59224`): 45 слоёв, 42 MoE-слоя, 288
маршрутизируемых экспертов, top-8, 1 общий эксперт, hidden 4096, FF эксперта 2048. Эксперт = 3×4096×2048 = 25.17M
параметров; при 4.5 bpw — 14 155 776 Б = 13.50 MiB (HYPOTHESIS-арифметика; совпадает с размером блоба 14155792 Б в
`docs/strata-tiered-run.md`@eb59224 — VERIFIED). Все 12 096 экспертов при 4.5 bpw — 171.2 ГБ; VRAM 4×32 GiB = 137.4 ГБ.
Для `UD-Q4_K_XL` измерено в репо: эксперты 177 528 MiB, плотная часть 8550 MiB (`PROBLEMS.md:62,64@eb59224`, PROVISIONAL —
замер на хосте 3090).

### 1.1. Статическое размещение по профилю маршрутизации

- **Суть.** Записать частоты (слой, эксперт) на корпусе промптов и заранее положить самые частые в VRAM; остальные — в
  закреплённую RAM.
- **Источники и цифры.**
  - Strata: кэш, заполненный по профилю, на held-out промптах даёт 50% попаданий при 4 500 слотах из 24 576 (VERIFIED,
    Strata-Paper.pdf §6 п.4 @fb58e0d; это авторский замер — REPORTED как число).
  - KTransformers, 4×RTX 4090, TP=4, Qwen3-Next-80B-A3B-FP8: стратегия `frequency` при 50% экспертов на GPU — 76.19 tok/s,
    при 80% — 100.67, при 0% — 52.72, при 100% — 114.26; `uniform` при 50% — 65.25 (VERIFIED, таблица в
    `doc/en/kt-kernel/experts-sched-Tutorial.md:178-190@2ac8cf9`; замер авторов — REPORTED; режим нагрузки — ShareGPT, не
    обязательно batch 1).
  - llama.cpp, статическое hot/cold на RTX 5090: Qwen3-Coder-Next 72.1→90–92 tok/s, gpt-oss-120B 36.2→47.6 tok/s,
    префилл −9.9% (REPORTED, комментарий JigSawPT в issue #20757, страница VERIFIED).
  - vLLM RFC #38256: статическое закрепление экспертов по статистике использования на GB300 для DeepSeek-V4.1-Flash
    MXFP4: C1 ~89→~153 tok/s (REPORTED, страница VERIFIED; GB300 — когерентная система, к PCIe не переносится).
- **Воспроизведено независимо?** Идея — да (три независимые реализации с похожим эффектом); числа — нет.
- **Применимость.** Прямая: профиль — это выход G0 (`tools/g0/`). Базы A и B уже читают профиль (`profile.bin` в
  `docs/strata-tiered-run.md`@eb59224 — VERIFIED).
- **Сложность.** Низкая (есть в обеих базах). **Лицензии:** Strata MIT, KTransformers Apache-2.0.
- **Риск.** Профиль с другого распределения задач (чат vs код агента) даёт заметно меньше попаданий: у Strata статический
  профиль 50% против 72% адаптивного (VERIFIED/REPORTED, там же).
- **Ожидаемый выигрыш (HYPOTHESIS).** При ~65–69% экспертов, помещающихся в VRAM (`docs/evidence/2026-10-03-lighttransport-fork.md`
  @eb59224: fitplan Q4_K → 68.5% — PROVISIONAL), и типичной для MoE асимметрии частот статический профиль даст h≈0.80–0.90.
  Вывод: при равномерной маршрутизации h равнялось бы доле резидентных (0.68); любая асимметрия поднимает h выше доли.
  Порог проверки — E4 в §10.

### 1.2. Адаптивный кэш: LRU, SLRU, LFRU, допуск по частоте

- **Суть.** Динамически подменять резидентные эксперты под текущий разговор; политика вытеснения и допуска.
- **Источники и цифры.**
  - Strata: каждые 4 раунда меняет до 96 экспертов, которые разговор запрашивает, на наименее используемые, пока GPU
    занят черновиком; 50%→72% попаданий; «вытеснить сразу, допускать новый только после завершения копии» дало
    91.7→94.4 tok/s (VERIFIED, Strata-Paper.pdf §3.4, §6 п.4 и п.10 @fb58e0d).
  - llama.cpp PR #27861 (черновик, не влит): LRU по слоям с `--moe-expert-cache N`, лимит загрузок за шаг; 2×RTX 3090
    Qwen3.8-Flash-Next UD-Q4_K_XL 18.4→24.2 tok/s при 48 слотах; на RTX PRO 4500 16.8→41.3 tok/s при 86.9% попаданий;
    работает только при `n_tokens == 1` (MTP/спекуляция обходят кэш) (REPORTED, страница VERIFIED).
  - llama.cpp issue #20757: предложение SLRU с допуском на втором промахе; в PoC стационарный режим ~98–100% попаданий на
    GPT-OSS-120B; низкий hit rate (44–58%) делает кэш медленнее, чем без него (REPORTED, страница VERIFIED; второе — в
    поисковой выдаче блога developersdigest, саму страницу открыть не удалось).
  - vLLM RFC #38256 / PR #37190: LFRU + межслойное предсказание; оценка Belady для OLMoE — 1.068× к достигнутому, т. е.
    запас предвыборки при batch 1 мал (REPORTED, страница VERIFIED).
  - SeqMoE (arXiv 2609.12978): при кэше 15–45% экспертов средний hit 84.6–97.0% против 60.0–88.5% у LRU (REPORTED, только
    выдача поиска).
  - Eliseev & Mazur (arXiv 2312.17238): простое LRU на слой для Mixtral (REPORTED, аннотация).
- **Воспроизведено?** Эффект «адаптивный > статический» виден в Strata, llama.cpp-форках и vLLM-обсуждении — качественно да.
- **Применимость.** Высокая: разговор агента (один репозиторий, один набор инструментов) локален по темам.
- **Сложность.** Средняя: асинхронные копии на отдельном потоке, подмена таблицы слотов только после завершения копии
  (иначе гонки — см. баг с дублирующими slot id в PR #27861, REPORTED).
- **Риск.** Детерминизм: смена набора резидентных экспертов не меняет математику, если GPU- и CPU-ядра считают одно и
  то же бит-в-бит; у базы B автор прямо пишет, что «CPU и GPU эксперты квантуют активации по-разному, попадания меняют
  логиты» (`docs/evidence/2026-10-03-lighttransport-fork.md`@eb59224, VERIFIED-цитата). Это конфликтует с требованием
  воспроизводимости.
- **Ожидаемый выигрыш (HYPOTHESIS).** +0.05…+0.2 к h поверх статического профиля (по аналогии с 0.50→0.72 Strata);
  по roofline (§9) переход h 0.8→0.95 на 4-канальной DDR4 даёт 35→41 tok/s для UD-Q4_K_XL.

### 1.3. Бюджеты по слоям

- **Суть.** Разное число слотов на слой; размер слота по реальному размеру эксперта слоя.
- **Источники.** AdapMoE (ICCAD'24, arXiv 2408.10284): DP-распределение кэша по слоям, −25% активируемых экспертов,
  ×1.35 (REPORTED, аннотация; адаптивный гейтинг меняет выход модели — не годится при «exact routing»). Strata: «размер
  кэша в байтах, а не в слотах» — 2 673→3 556 экспертов IQ3_XXS и +13% декода при 1K (VERIFIED, Strata-Paper.pdf §6 п.8).
  KTransformers `--kt-num-gpu-experts` — равномерно на слой (VERIFIED, experts-sched-Tutorial.md:133).
- **Применимость.** Прямая: `UD-Q4_K_XL` — смесь квантов по тензорам, размеры экспертов разных слоёв различаются
  (HYPOTHESIS по названию «UD»; проверить по GGUF).
- **Ожидаемый выигрыш (HYPOTHESIS).** Единицы процентов к h; почти бесплатно.

### 1.4. Исполнение промахов на CPU (co-execution)

- **Суть.** Эксперт, которого нет в VRAM, считается на CPU прямо из RAM; GPU параллельно считает попавшие.
- **Источники и цифры.**
  - Fiddler (ICLR'25): ×1.26 для batch 1, ×1.30 длинный префилл, ×11.57 beam search; код github.com/efeslab/fiddler
    (REPORTED, аннотация/proceedings в выдаче).
  - KTransformers (SOSP'25, DOI 10.1145/3731569.3764843): AMX-ядра и асинхронный планировщик, ×1.25–4.09 декод;
    «Expert Deferral» +до ×1.45 при падении точности ≤0.5% (REPORTED, аннотация в выдаче; PDF недоступен — 403).
  - HybriMoE (arXiv 2504.05897, на базе kTransformers): ×1.70 декод, ×1.33 префилл (REPORTED, аннотация).
  - DAOP (DATE'25): предвычисление предсказанных экспертов на CPU приближёнными методами (REPORTED; приближение — не наш
    случай).
  - Strata: GPU пишет 10 id экспертов в «дверной звонок» в pinned-памяти, CPU-поток крутится на нём и сразу делит
    эксперты: попавшие — GPU, часть промахов — DMA по PCIe, остальное — CPU; весь 48-слойный проход — один CUDA graph
    (VERIFIED, Strata-Paper.pdf §3.2). Раунд Q2_0 при 4K: 34.3 мс = GPU 14.6 + ожидание CPU 13.4 + черновик 2.0 + прочее
    4.3 (VERIFIED, табл. 5).
- **Воспроизведено?** Принцип воспроизведён многократно (Fiddler, kTransformers, Strata, llama.cpp `-ot exps=CPU`/`--n-cpu-moe`
  — последнее VERIFIED, `tools/server/README.md:81-82@79e2e74`).
- **Применимость.** Высокая: 48 ядер Zen 3 с запасом по вычислениям над полосой DDR4 при batch 1 (§4).
- **Сложность.** Есть в базах A и B. **Риск.** «Expert Deferral» и DAOP меняют вычисление — противоречат exact routing
  (неприменимы при exact routing: по аннотации KTransformers потеря точности до 0.5% — REPORTED).
- **Ожидаемый выигрыш (HYPOTHESIS, §9).** CPU добавляет свою полосу к GPU: при h=0.8 и 8 каналах roofline даёт 58.5 tok/s
  против 53.5 при h=1 (18B@4.5 bpw) — промахи на CPU параллельны GPU-попаданиям.

### 1.5. Предсказание экспертов и упреждающая подкачка

- **Суть.** Угадать эксперты слоя l+1 (или токена t+1) заранее и начать копию до роутера.
- **Источники и измеренная точность.**
  - Pre-gated MoE (ISCA'24): требует **обучения** функции пре-гейта; на SwitchTransformer +23% накладных к GPU-only,
    −4.2× пик памяти (VERIFIED, camera-ready PDF, введение). Для наших моделей без дообучения — неприменимо.
  - Eliseev & Mazur: применяют гейт следующего слоя к скрытому состоянию текущего (REPORTED, по пересказу в выдаче).
  - FloE (arXiv 2505.05950): косинусное сходство скрытых состояний соседних слоёв >0.95 у Mixtral, кроме первого слоя
    (REPORTED, выдача).
  - FATE (arXiv 2502.12224): межслойный гейт, hit до 99% (REPORTED, выдача; edge-модели).
  - ProMoE (arXiv 2410.22134): обученный предсказатель со «stride»; декод ×2.07 к выгрузке, ×1.34 к ручным кэшам (v3)
    (REPORTED, аннотация; цифры разных версий различаются).
  - MoE-Infinity (arXiv 2401.14361): трассировка активаций на уровне запроса для prefetch/кэша (REPORTED, аннотация).
  - fMoE/FineMoE (arXiv 2502.05370, EuroSys'26): −47% задержки, +39% hit (REPORTED, аннотация).
  - ExpertFlow (arXiv 2410.17954): трансформер-предсказатель маршрута (REPORTED, аннотация).
  - «Speculating Experts» (arXiv 2603.19289): «квази-скрытое состояние» → эксперты следующего слоя, до −14% TPOT к
    загрузке по требованию (REPORTED, выдача).
  - HOBBIT (arXiv 2411.01433): при промахе грузит версию эксперта пониженной точности — **меняет выход** (REPORTED; для нас
    неприемлемо при exact routing).
  - **Отрицательный:** обученный предсказатель по истории маршрутов дал ~25% recall@top-8 при 3.1% случайных и **ни разу не
    обошёл «повторить маршрут предыдущего токена»**; проект перешёл на нативный гейт следующего слоя (REPORTED, issue
    aosama/astronomical #594, страница VERIFIED).
  - База A (strata-glm) уже предсказывает эксперты слоя l+1 по потокам слоя l (`docs/design/G4-glm-multigpu.md:43-44@eb59224`,
    PROVISIONAL — прочитано в коде, не запускалось).
- **Применимость.** Только бесплатные предсказатели: гейт слоя l+1 по состоянию слоя l (нужна модель mHC: какой из 4
  потоков подавать — открытый вопрос, UNKNOWN) и повтор маршрута предыдущего токена. При pipeline-разбиении 3 карты из 4
  простаивают, их PCIe-линки свободны — предвыборка может идти по ним (`docs/design/G4-glm-multigpu.md:46-47`, PROVISIONAL).
- **Риск.** Неверная предвыборка тратит полосу DRAM, которую CPU использует для промахов (Strata: DMA при DRAM-ограниченном
  CPU только отнимает полосу — VERIFIED, §6 п.9).
- **Ожидаемый выигрыш (HYPOTHESIS).** При recall@16 ≈0.85 и 3 свободных линках по ~24 ГБ/с предвыборка может перевести
  часть промахов из CPU-времени в «уже в VRAM»; верхняя граница — переход к точке h_eff≈h+0.1 на кривой §9 (≈+3…+6 tok/s).
  Если recall@16 < 0.6 — не строить (E5).

### 1.6. Системы для пропускной способности (не batch 1)

MoE-Lightning (arXiv 2411.11217; CGOPipe, до ×10.3 на T4), Klotski (arXiv 2502.06888; до ×85 на многобатчевом конвейере),
MoE-Lens (arXiv 2504.09345), FlexGen (ICML'23; OPT-175B, 1 tok/s при эффективном батче 144) — REPORTED по аннотациям.
**Для одиночного потока неприменимо** (их выигрыш — от батча, амортизирующего загрузку). Полезны как модели производительности
(«иерархический roofline» MoE-Lightning).

### 1.7. Префилл, ориентированный на экспертов

- Strata: в префилле чанками 2048 токенов промахнувшиеся эксперты копируются по PCIe, пока GPU считает предыдущие;
  префилл почти плоский от 4K до 262K (539→496 tok/s) и упирается в запуски ядер и fp16-деквантизацию, используя ~7 из
  26 ГБ/с PCIe (VERIFIED, Strata-Paper.pdf §3.5, §6 п.11).
- llama.cpp: операции над весами в RAM переносятся на GPU при батче ≥32 (`GGML_OP_OFFLOAD_MIN_BATCH`, по умолчанию 32;
  VERIFIED, `ggml/src/ggml-cuda/ggml-cuda.cu:6037@79e2e74`).
- llama.cpp PR #25294: «волны» экспертов в префилле, когда убатч трогает больше экспертов, чем слотов (REPORTED).
- KTransformers Layerwise Prefill для GLM-5.3-Flash обнуляет резидентные GPU-эксперты на время префилла (VERIFIED,
  `GLM-5.3-Flash-Tutorial.md:90@2ac8cf9`).
- На нашей машине уже измерено (база A, 1×3090, синтетический пак): 438 tok/s @16K, 421 @64K при `--chunk 4096`
  (`docs/strata-tiered-run.md`@eb59224, PROVISIONAL — тестовый пак).
- **HYPOTHESIS:** 4 карты с 4 линками дают до 4× полосы стриминга экспертов в префилле, но общий источник — DRAM: при
  4 каналах ~82 ГБ/с суммарно (§9).

### 1.8. CPU против PCIe: точка безубыточности для эксперта 13.5 MiB (HYPOTHESIS, расчёт)

Скрипт расчёта — `scratchpad/calc/roofline.py` (не в репо). Допущения: PCIe 4.0 x16 H2D 24 ГБ/с (замер-пробы Strata на
4080 Super 32 GB: 24.0 ГБ/с — VERIFIED как текст отчёта `bench/results/2026-10-04-community-rtx-4080s-iq3s/README.md:27@fb58e0d`;
на EPYC 7453 в KVM — 23–26 ГБ/с, там же `2026-09-29-rtx3090-epyc-milan/README.md:43`), DDR4-3200 с КПД 0.8:
4 канала 82 ГБ/с, 8 каналов 164 ГБ/с, VRAM 736 ГБ/с × 0.8.

| путь для одного эксперта (14.16 МБ) | время |
|---|---|
| копия по PCIe | 0.590 мс |
| затем GPU-GEMV | 0.024 мс |
| CPU, ограничение DRAM, 4 канала | 0.173 мс |
| CPU, ограничение DRAM, 8 каналов | 0.086 мс |

Вычислительная стоимость на CPU: 2×25.17M = 50.3 MFLOP на токен-эксперт; при 0.75–1.5 TFLOP/с (UNKNOWN для AVX2 Q4_K на
этом CPU — оценка) это 0.034–0.067 мс на токен. **PCIe окупается, когда на эксперта приходится ≳9–18 токенов** —
префилл и большие окна верификации; в декоде с окном ≤8 выгоднее CPU. Согласуется с порогом 32 у llama.cpp (VERIFIED выше)
и с выбором Strata (CPU в декоде, стриминг в префилле). Важное следствие: DMA-доля промахов полезна, **только если CPU
ограничен вычислениями, а не DRAM** (Strata §6 п.9: i-кванты +10–16% с 55% промахов по DMA; Q2_0 — DMA только мешает).
Оптимальная доля при вычислительном ограничении f = BW_pcie / (BW_pcie + BW_cpu_compute) (HYPOTHESIS).

## 2. Несколько GPU при batch 1 по PCIe без NVLink

### 2.1. Конвейер по слоям (pipeline)

- **Суть.** Слои делятся на диапазоны по картам; токен переходит между картами раз на окно; у каждой карты свой кэш
  экспертов её слоёв.
- **Цифры.** Strata: «один переход на окно верификации (несколько сотен КБ через pinned RAM), без NVLink и P2P»; 5080+3090
  декод 84/110 против 83–87/88–105 у одной 5080, префилл +18–20%; «декод на уровне более быстрой карты»; **третья, более
  медленная карта (2080 Ti) замедлила пару до 68/90** (VERIFIED, `docs/MULTI_GPU.md:9-10,185-196@fb58e0d`; замер — REPORTED).
  EPYC 7453 + 2×3090 (KVM): IQ3_XXS при 32K 1 карта ~90.6, 2 карты 96.7 tok/s; IQ3_S 2 карты 106.3 (VERIFIED как отчёт,
  `bench/results/2026-09-29-rtx3090-epyc-milan/matrix.md:9-21@fb58e0d`).
- **Наш дизайн.** Передача между стадиями — состояние mHC 4×4096 fp32 = 64 КиБ на токен на границу
  (`docs/design/G4-glm-multigpu.md:38-40@eb59224`, VERIFIED как текст дизайна). На PCIe 4.0 это ~3 мкс передачи + задержка
  запуска; 3 границы на токен — пренебрежимо (HYPOTHESIS).
- **Ограничение (HYPOTHESIS, §9).** Полоса VRAM не суммируется: декод ограничен одной картой. Pipeline даёт **ёмкость**
  (больше экспертов в VRAM), но не скорость чтения плотной части.
- **Сложность.** Этап 1 уже написан в патче 0002 базы A и бит-экзактен на 1×3090 (`docs/PLAN.md` строка G4@eb59224, PROVISIONAL).

### 2.2. Тензорный параллелизм (TP)

- **ik_llama.cpp `-sm graph`** (PR #1022): 2×3090, GLM-4.5-Air: tg при пустом контексте 60.51 (graph) против 91.78 (layer);

  длинном контексте (~36 против 17) (REPORTED, hackernoon в выдаче).

### 2.3. Экспертный параллелизм и «карты-помощники»

- Strata `--expert-cache-device1..3`: эксперты на вспомогательных картах, результаты возвращаются через pinned-память

  `docs/SECOND_GPU.md:122-123@fb58e0d`; REPORTED как замер).
- KTransformers: GLM-5.3-Flash с `--tp-size 4` на SM89 (VERIFIED, `GLM-5.3-Flash-Tutorial.md:15,47@2ac8cf9`) — TP плотной
  части в SGLang + эксперты на CPU; но CPU-ядро AVX-512 FP8 (§4.1).
- **HYPOTHESIS.** EP через хост без P2P на каждом слое (42 круга на токен) проигрывает CPU-пулу; EP имеет смысл только с
  P2P и коллективами ≲20–30 мкс.

### 2.4. P2P на GeForce и внутри VM

- Патч драйвера (tinygrad → aikitoria): P2P через BAR1 для RTX 30/40/50; **нужен Resizable BAR с BAR1, отображающим всю VRAM,

  32 GB размер BAR1 = 32 GiB не гарантирован VBIOS (UNKNOWN).

  быстро» (REPORTED, форум Proxmox в выдаче). Заказчик утверждает «P2P работает» (`hardware/4x4080s-32g.json`, VERIFIED как
  заявление заказчика в файле) — **на уровне латентности не измерено** (UNKNOWN).
- Эффект P2P на vLLM TP: от +2–5% до −5–7% (2×5090) и +50% (4×3090, Reddit) — разброс (REPORTED).

### 2.5. Спекулятивный конвейер (занять простаивающие стадии)

меньше, но это единственный известный способ занять 3 простаивающие карты без TP.

## 4. CPU: AVX2-ядра, полоса DDR4, NUMA

### 4.1. AVX2-ядра для Q4_K/INT4 MoE

- **llama.cpp / ggml:** AVX2-реализации K-квантов. Strata измерила: i-кванты (IQ2/IQ3) на CPU ограничены арифметикой —

## 5. NVMe-ярус

### 5.1. Способ чтения: O_DIRECT/io_uring/mmap

- Strata (ярус n-gram на SSD): по умолчанию **небуферизованные чтения 4 КиБ**, до 256 запросов в полёте («декоду нужно 16;
  чанк префилла насыщает SSD на 256»), ограниченный кэш строк (1 048 576 строк, ~95–335 МБ), отдельный I/O-поток.
  **Отображённая в память секция того же файла сериализует небуферизованные чтения: 311 → 1 575 мкс на токен**; есть
  «keepalive», чтобы SSD не засыпал между запросами (VERIFIED, `include/strata/kernels/ngram.hpp:140-165@fb58e0d`;
  замер Windows — REPORTED).
- llama.cpp PR #25294 (не влит): стриминг экспертов с диска с O_DIRECT и пулом асинхронного I/O, «decaying hotness + LRU»;
  GB10, GLM-5.2 UD-Q2_K_XL: декод 1.83–2.20 tok/s при 73–79% попаданий против 0.87 у mmap+`--cpu-moe` (REPORTED, страница VERIFIED).
- SQPOLL не даёт прироста IOPS при насыщении устройства и ухудшает хвост задержки (REPORTED, препринт preprints.org 202609.1021).
- **HYPOTHESIS.** Для экспертов 13.5 MiB — O_DIRECT большими чтениями (≥1 MiB) в pinned-буфер; для строк Engram — O_DIRECT
  4 КиБ через io_uring с глубокой очередью; mmap — только как A/B-плечо (страничный кэш съест RAM, которой и так мало).

### 5.2. RAID0 против раскладки по файлам

Прямых сравнений для LLM не нашёл (UNKNOWN). HYPOTHESIS: для крупных чтений эксперта RAID0 (чанк 512 КиБ–1 МиБ) даёт
параллелизм внутри одного эксперта; раскладка «эксперт e → диск e mod N» даёт независимые очереди без синхронизации полос.
При 8+ одновременных промахах на слой оба варианта насыщают все диски; выбирать по p99 в E10. **Число дисков не согласовано:
`AGENTS.md`/`hardware/4x4080s-32g.json` — 3×990 Pro, постановка R3 — 4×1 ТБ (UNKNOWN).** *Поправка 2026-10-12: заказчик —
3 × 1 ТБ; расчёты этого файла «при 3 дисках» остаются в силе, модели дисков — UNKNOWN до R0 (`docs/evidence/2026-10-12-n26b-nvme-3x1tb.md`).*

### 5.3. GPUDirect Storage на GeForce и в VM

- cuFile имеет режим совместимости (POSIX-чтение в RAM + копия на GPU), `allow_compat_mode` по умолчанию true (REPORTED,
  документация cuFile в выдаче). Старая матрица поддержки (GDS 1.0) — только T4/A10/A100/V100/Quadro (REPORTED).
- Поддержка GeForce в прямом режиме — UNKNOWN; внутри Proxmox-VM прямой путь NVMe→GPU требует nvidia-fs и согласованного
  IOMMU — HYPOTHESIS: недоступен. Совместимый режим не быстрее собственного O_DIRECT + `cudaMemcpyAsync`.

### 5.4. Samsung 990 Pro 1 ТБ

- 7 450 МБ/с последовательное чтение; 1 200K IOPS 4K QD32 (часть листингов пишет 1 400K) (REPORTED, ритейлеры/NASCompares;
  даташит Samsung не открывался).
- Тепло: в стресс-тесте Tom's Hardware без радиатора держал полную скорость, не дойдя до 70 °C; в форуме есть одно

  (VERIFIED, ngram.hpp:159-163). На сервере проверить `nvme get-feature -f 0x0c`.

### 5.5. Работы по SSD-выгрузке

- FlexGen (ICML'23): пропускная способность, батч 144 (REPORTED) — не для batch 1.
- LLM in a flash (Apple, arXiv 2312.11514): «windowing» и «row-column bundling», модели до 2× DRAM, ×4–5 CPU и ×20–25 GPU к
  наивной загрузке (REPORTED).
- PowerInfer-2 (arXiv 2406.06282): нейронные кластеры, конвейер I/O на UFS (REPORTED).
- «SSD Offloading … Considered Harmful in Energy Efficiency» (arXiv 2508.06978): до ~12× энергии на токен к HBM, предвыборка
  скрывает задержку, но не энергию (REPORTED; симуляция).
- Flash-MoE (Qwen3.5-397B на MacBook 48 ГБ): 4.36 tok/s, SSD 17.5 ГБ/с, ~71% попаданий страничного кэша (REPORTED, блог).
- **HYPOTHESIS (§9).** При 3 дисках ~22 ГБ/с последовательного чтения 1% маршрутизируемых байт с SSD стоит ~2.1 мс на токен,
  5% — ~10.6 мс. **Эксперты на SSD допустимы только как хвост ≤1–2% трафика**; для GLM-5.3-Flash Q4 (171–186 ГБ) VRAM+RAM
  (~137+~110 ГБ) вмещают всё — SSD-ярус экспертов не нужен. Нужен для DeepSeek-V4.1-Flash (эксперты 268.9 GiB — VERIFIED как
  текст fact sheet `docs/models/deepseek-v4.1-flash.md:12@eb59224`).

## 6. Таблицы поиска на SSD: Engram, PLE, n-gram Strata

### 6.1. DeepSeek Engram

- **Как адресуется (VERIFIED по коду в репо, `third_party/deepseek-v41-flash/inference/`@eb59224, upstream 2cba9e4).**
  Хэши n-грамм считаются **до прохода слоёв** из id токенов (`model.py:1252`), затем в слоях 1 и 14 добавляются в поток
  (`model.py:1262-1263`). На позицию: 3 n-граммы (2-,3-,4-) × 8 голов = 24 строки на слой (`engram.py:171-184`,
  `config.json`: `engram_layer_ids [1,14]`, `engram_max_ngram_size 4`, `engram_n_heads 8`, `engram_head_dim 256`).
  Строка — 256 Б FP8 + 8 Б масштабов E8M0 на блок 32 (`model.py:27,30,296-325`) = 264 Б.
- **Байт на токен (HYPOTHESIS-арифметика):** 2 слоя × 24 × 264 Б = 12 672 Б полезных; при чтении страницами 4 КиБ —
  196 608 Б (усиление 15.5×); при 100 tok/s — 4 800 случайных чтений/с на всю систему (против ~1.2M IOPS в паспорте одного
  диска). Полоса не проблема; **проблема — задержка**.
- **Окно упреждения.** Слой 1 — почти самый первый: до него лишь эмбеддинг и слой 0, т. е. ~1/40 времени токена (~0.25 мс
  при 100 tok/s) — меньше типичной задержки случайного чтения NVMe (Strata: 311 мкс на 16 строк на токен — REPORTED).
  Значит: (а) хэш токена t+1 известен, как только t+1 выбран, — запускать чтения сразу после семплирования;
  (б) при спекуляции хэши черновых токенов известны заранее — читать строки для всего окна черновика во время проверки
  предыдущего; (в) слой 14 имеет большой запас. (HYPOTHESIS.)
- **Статья (VERIFIED, `Engram_paper.pdf` §2.5, §6.4, табл. 4 @fb7f84a):** «детерминированная адресация позволяет prefetch
  из host memory»; таблица 100B параметров целиком в DRAM хоста, слой во втором блоке, H800, 512 последовательностей:
  9 031.62→8 858.28 tok/s (4B dense) и 6 315.52→6 140.02 (8B dense), штраф ≤2.8%. Многоуровневый кэш (HBM/DRAM для частых,
  **NVMe для хвоста** по Ципфу) — предложен, **не измерен** в статье (VERIFIED по тексту §2.5). Замер — батчевый, на H800, не
  batch 1 и не SSD.
- **Применимость.** Только третья модель (DeepSeek-V4.1-Flash): таблицы 189.1 GiB не влезают в 128 ГБ RAM → SSD + DRAM-кэш
  строк. **Сложность:** средняя (у Strata есть `ngram.hpp` с Direct-чтением, MIT). **Риск:** p99 задержки SSD в VM.
- **Ожидаемое (HYPOTHESIS).** Распределение Ципфа → кэш строк 1–4 ГБ в DRAM снимет большинство чтений; остаток 4K O_DIRECT
  при глубине очереди 48 и упреждении на 1 токен (или на окно черновика) укладывается в бюджет <1 мс на токен.

### 6.2. Gemma 3n PLE

Официальная документация: параметры Per-Layer Embedding «могут кэшироваться на быстрое локальное хранилище» и подгружаться

### 6.3. N-gram таблица Strata (Qwen3.8-Flash-Next)

≈122 tok/s в пике одной карты (736/6.0) и ≈98 при КПД 0.8 — до учёта весов.

  `qk rope 0` (VERIFIED, fact sheet), т. е. весь латент квантуется.
- Strata: int8 KV выше 8K (32K в разделе результатов), иглы 3/3 на 8–28K (VERIFIED/REPORTED, Strata-Paper §3.7; бенчмарк

### 7.4. Ярусы KV: GPU → RAM → NVMe

- vLLM `OffloadingConnector`: CPU-ярус (pinned) + вторичные ярусы `fs`, объектное хранилище, P2P через NIXL; GPU↔CPU по DMA;
  вторичные ярусы — только через CPU; имена файлов — по хэшу содержимого блока с фиксированным seed (VERIFIED,
  `docs/features/kv_offloading_usage.md:3,11-15,145-188@ed7ae70`).
- LMCache: CPU RAM, локальный SSD, Mooncake, GDS и др. (VERIFIED, `README.md:69,73@ee68e5b`).
- SGLang HiCache: GPU L1 / host L2 / хранилище L3; до ×6 пропускной и −80% TTFT в блоге авторов (REPORTED).
- llama.cpp server: `--cache-ram` (кэш промптов в RAM, по умолчанию 8192 MiB), `--ctx-checkpoints` (до 32 на слот для
  SWA/рекуррентных), `--slot-save-path` (VERIFIED, `tools/server/README.md:166-168,226@79e2e74`).
- Strata: перекрытие загрузки KV из RAM с вычислением префилла (`STRATA_KV_PREFETCH=1`, VERIFIED, `docs/KV_PREFETCH.md`).

### 7.5. Префиксный кэш для KDA/GDN/Mamba-слоёв

- **vLLM:** `mamba_cache_mode` ∈ {`align`, `none`}; `align` — кэшировать состояние только в позициях i×block_size; опция
  `enable_mamba_shared_prefix_checkpoint` добавляет снимок в точке расхождения общего префикса; есть ReplaySSM и
  «Kimi-K3 KDA RecoverSSM speculative decode» (VERIFIED, `vllm/config/cache.py:63,189-218@ed7ae70`; документация
  `docs/features/automatic_prefix_caching.md:16-31`).
- **SGLang:** `MambaCheckpointPool` — кэшированные состояния KDA/GDN/Mamba2 хранятся **в int8** (по (голова, k-канал)),
  «~2× больше состояний», деквантизация один раз при попадании, сочетается с выгрузкой в host (VERIFIED,
  `python/sglang/srt/mem_cache/mamba_checkpoint_pool.py:15-40@46c2585`).
- **LMCache:** Kimi-Linear (KDA + MLA) — состояние KDA трактуется как непрозрачная страница, префиксный кэш работает
  «end to end» (VERIFIED, `docs/source/recipes/kimi_linear.rst:1-12@ee68e5b`).
- **Strata:** снимок на границе предыдущего хода агента (`STRATA_CACHE_MESSAGE_BOUNDARY=1`) — переиспользует историю при
  правке последнего сообщения (VERIFIED, `docs/MESSAGE_BOUNDARY_CACHE.md`); в статье: сохранение рекуррентного состояния
  «несколько сотен МБ» превратит 30-секундное перечитывание в доли секунды — «крупнейший выигрыш для агентов» (VERIFIED, §7).
- Tail-Replay (arXiv 2608.30310): хранить точный KV полного внимания, а состояние линейного внимания восстанавливать
  повтором короткого хвоста (REPORTED, выдача).
- **HYPOTHESIS для GLM.** Снимок 34 KDA-слоёв = 136 MiB fp32 (~34 MiB в int8 по схеме SGLang) + conv-окна; точки снимков:
  конец системного промпта, конец каждого хода, каждые N=8–16K токенов. 30 снимков int8 ≈1 ГБ RAM.

### 7.6. Целостность сохранения/восстановления

HYPOTHESIS (требования): ключ = хэш-цепочка id токенов + отпечаток (модель, квант, токенизатор, версия движка, dtype KV);

кванта общий каталог между разными квантами опасен (HYPOTHESIS).

## 9. Физический roofline batch-1 декода (PROVISIONAL / HYPOTHESIS)

Обозначения: `bpw` — бит на вес; `A_d` — активные параметры, читаемые на каждый токен всегда (attention/KDA/DSA, общий
эксперт, плотные слои 0–2, mHC, lm_head); `A_r` — активные маршрутизируемые параметры; `h` — доля байт маршрутизируемых
экспертов, обслуженных из VRAM; `B_ctx` — байты состояния и KV на токен.

```
B_d = A_d·bpw/8          B_r = A_r·bpw/8
VRAM-байт/токен = B_d + B_ctx + h·B_r
DRAM-байт/токен (CPU считает промахи) = (1−h)·B_r          PCIe-байт/токен (если промахи копировать) = (1−h)·B_r
t_pre  = (B_d + B_ctx) / (η_v·BW_v)                        — до роутера, только GPU
t_hit  = h·B_r / (η_v·BW_v)                                — GPU-эксперты
t_miss = (1−h)·B_r / (η_d·BW_dram)                         — CPU-эксперты (DRAM-предел)
t_tok  ≈ t_pre + max(t_hit, t_miss) + L·t_sync             (полное перекрытие внутри слоя; без перекрытия — сумма)
Спекуляция: t_pass = (B_d + B_ctx + U(k)/8·B_r)/(η_v·BW_v), t_tok = t_pass / a;  U(k) = 288·(1−(1−8/288)^k)
TP4+EP4:   t_tok ≈ (B_d+B_ctx)/(4·η_tp·BW_v) + max(h·B_r/(4·η_tp·BW_v), t_miss) + 90·t_allreduce
SSD-доля s: t_ssd = s·B_r / BW_nvme
```

Подстановка (PROVISIONAL): A = 18B, A_r = 42×8×25.17M = 8.46B (геометрия GLM — VERIFIED), A_d = 9.54B (остаток до 18B),

0.104 ГБ); BW_v = 736 ГБ/с, η_v = 0.8; DRAM η_d = 0.8 (4 кан. 82 ГБ/с, 8 кан. 164 ГБ/с); t_sync = 20 мкс × 42 слоя;

SSD: 1% маршрутизируемых байт — 48 МБ/токен → 2.1 мс при 3×7.45 ГБ/с; 5% — 238 МБ → 10.6 мс.
Engram: 12 672 Б полезных/токен, 196 608 Б страницами 4 КиБ, 4 800 IOPS при 100 tok/s.

**Выводы из roofline (HYPOTHESIS).**
1. Pipeline на 4 картах с весами ~4.5 bpw не даёт 50 tok/s на GLM-5.3-Flash `UD-Q4_K_XL` ни при каком h; для 18B «чистых»
   4.5 bpw — впритык (53–58 tok/s при h≥0.8 и 8 каналах).
2. 80–100 tok/s достижимы только комбинацией: TP/EP с коллективом ≲20–30 мкс **и** h≥0.9 **и** (8 каналов или спекуляция).
3. При 4 каналах DDR4 CPU-ярус проигрывает GPU-попаданиям в ~2 раза; каждая +0.05 к h стоит дороже любого ядра.
4. Модель не учитывает: накладные запуски ядер (КПД MoE-GEMV ≈0.5 у llama.cpp), вычисления внимания/индексера, ожидание
   DMA, неравномерность по слоям. Реальные числа будут ниже.

## 11. Негативные результаты (что не сработало или неприменимо)

1. **Перекрытие двух групп токенов внутри слоя** (CPU одной группы параллельно GPU другой) — точно, но на 7% медленнее
   (85.8 против 91.8 tok/s): плотные веса читаются дважды (VERIFIED, Strata-Paper §6 п.5).
2. **Карта-помощник с экспертами через хост** (без P2P) замедлила декод; дубли слотов → 43 мс ожидания вместо 19, 40 против
   66 tok/s (VERIFIED как текст, `docs/SECOND_GPU.md:122-123@fb58e0d`).
3. **Третья, более медленная карта в pipeline** замедлила пару (68/90 против 84/110) (VERIFIED как текст, MULTI_GPU.md:196).
4. **TP в llama.cpp для MoE** — gpt-oss-120B ×1.00; pp при малой глубине ×0.41–0.91; Llama-8B Q4_0 на 2×4090 175→102 tg
   в первой версии PR (REPORTED). ik_llama `graph` при пустом контексте 60.5 против 91.8 tg (REPORTED).
5. **vLLM custom all-reduce на >2 PCIe-картах без NVLink — выключен кодом** (DISPROVED как вариант; VERIFIED, §2.2).
6. **Machete на Ada** — только sm90 (DISPROVED, VERIFIED, §3).
7. **KTransformers для GLM-5.3-Flash на нашем CPU как есть** — нужен AVX-512 FP8 и ≥350 ГБ RAM (DISPROVED, VERIFIED, §4.1).
8. **Pre-gated MoE без дообучения** — неприменим: пре-гейт обучается (VERIFIED, camera-ready PDF).
9. **Обученный предсказатель маршрутов по истории** не обошёл «повтор маршрута предыдущего токена» (REPORTED, issue #594).
10. **Низкий hit rate делает кэш экспертов медленнее**, чем стриминг без кэша (44–58% — REPORTED); на Metal кэш с
    синхронизацией на слой уронил Qwen3-30B 40.4→20.2 tok/s; staging-предвыборка на M4 — ×0.94–0.95 (REPORTED, issue #20757,
    RFC #38256).
11. **DMA-доля промахов при DRAM-ограниченном CPU** только отнимает полосу (Strata Q2_0 оставлен на 20%) (VERIFIED, §6 п.9).
12. **Одновременная mmap-секция и небуферизованные чтения** того же файла: 311→1 575 мкс на токен (VERIFIED как текст, ngram.hpp:144-146).
13. **FP8-внимание на 128K** до исправления накопления: NIAH ~91%→~13% (REPORTED).
14. **SQPOLL** не увеличивает IOPS при насыщении устройства (REPORTED).
15. **SSD-выгрузка экспертов энергетически дорога** — до ~12× энергии на токен (REPORTED, симуляция).
16. **Expert Deferral (KTransformers), HOBBIT, AdapMoE, MoE-Spec, DAOP** — дают скорость ценой изменения вычисления
    (пропуск/замена/понижение точности экспертов); **несовместимы с требованием exact routing** (HYPOTHESIS по их аннотациям).
17. **Кэш экспертов llama.cpp (#27861) не обслуживает многотокенные окна** (MTP/спекуляция обходят кэш; дубли slot id ломают
    батчевые ядра при n>1) (REPORTED).
