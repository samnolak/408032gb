# D1: политика GPU-кэша экспертов в llama.cpp (`--moe-cache-mib`) — первый кандидат направления D

Статус: дизайн, NOT RUN. Применимо к ярусным кандидатам (GLM-5.3-Flash, DeepSeek-V4-Flash-0731, MiMo-V2.6-Flash), если R1
покажет llama.cpp лучшим движком для них. Для Qwen3.8-Flash-Next (всё в VRAM) не нужно.

## Как работает сейчас (CONFIRMED чтением кода, llama.cpp `src/llama-moe-cache.cpp` @10a60cf30; коммиты `d6cf9acb2`, `c811cb8f0`)
- Эксперты лежат в RAM хоста; на GPU — банки слотов. **Один LRU на группу слоёв одного устройства** (строки 15–120, 166–175);
  бюджет устройства делится между группами пропорционально байтам экспертов (строки 310–327) — на 4 GPU это ≥ 4 независимых LRU.
  В симуляторе это приближает политика `lru_device` (смежные слои по устройствам, промпт > 32 токенов только читает кэш);
  несколько групп на устройство при смешанных типах тензоров по слоям — не моделируются.
- На каждом MoE-слое при батче ≤ 32 токенов: синхронизация устройства, чтение выбранных экспертов, LRU-план, **синхронная
  подгрузка промахов по PCIe** (H2D), затем счёт на GPU (функция `copy`, строки ~515–560). CPU-счёта промахов в этом пути нет.
- Батчи > 32 (префилл) кэш обходят, чтобы не вытеснять эксперты генерации (строки 468–470).

## Гипотезы улучшения (каждую сначала проверяет симулятор, затем бенчмарк)
| # | изменение | основание | как проверить |
|---|---|---|---|
| H1 | предзагрузка по профилю маршрутизации + допуск TinyLFU вместо чистого LRU | на синтетике static/TinyLFU > LRU; на трассах реальной модели — UNKNOWN; повтор эксперта t→t+1 у GLM 24.6% (REPORTED, база A) — перекос может быть слабым | `tools/g0/cachesim.py` на трассах M1: `lru_device` против `opt_global`, `static`, `tinylfu` при той же ёмкости, колонка `gen`, с `--session` и без |
| H2 | бюджет по слоям вместо общего LRU | слои с разной «концентрацией» маршрутизации | cachesim: `lru` (по слою) против `lru_global` |
| H3 | промах при batch=1 считать на CPU (эксперт уже в RAM), а не копировать по PCIe | roofline: PCIe 25 ГБ/с против ~140 ГБ/с RAM; порог `GGML_OP_OFFLOAD_MIN_BATCH=32` в самом llama.cpp (R3) | замер M4; требует разделения MUL_MAT_ID между бэкендами — сложность высокая |
