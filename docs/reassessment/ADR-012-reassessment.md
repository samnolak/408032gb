# ADR-012. Переоценка 2026-10-09: платформа «сначала измерения», модель и движок выбираются по железу заказчика

**Статус:** ПРИНЯТО ПРЕДВАРИТЕЛЬНО (ведущий агент переоценки, 2026-10-09). Окончательные пункты D2 (модель) и D3 (движок)
подтверждаются или меняются только по результатам гейтов R1–R2 (`ROADMAP.md`). Заменяет как рамку проекта: ADR-001, 002, 005
(вариант IQ2/IQ3), 006 (частично), 010 (п. 2–3); переводит в REVALIDATE/заморозку ADR-003, 007, 009, 011. Классификация —
`LEGACY_AUDIT.md`. Старые ADR не удаляются; в `docs/DECISIONS.md` ставится ссылка на этот документ.

## Контекст

1. **Новые требования заказчика** (мастер-промпт 2026-10-09) выше исторических решений: лучшее практическое качество open-weight
   моделей для code-агентов/рассуждений/tool use/длинных документов; **≥ 262 144 реально используемых токенов**; single-stream декод
   **50 tok/s минимум, 80–100+ желательно** при заполненном контексте; основные веса **≥ качественного 4-бит**; точная маршрутизация;
   VRAM→RAM→SSD там, где окупается; сервер с API и кэшем префиксов.
2. **Аудит репозитория** (`REPO_AUDIT.md`): своего GPU-кода нет; ни одного запуска на 4×4080; единственный замер на реальных весах —
   ik_llama.cpp на 1×3090 (15.0 tok/s, 8K); 262K и Q4-минимум в старом плане не учтены; P2P и состав железа — заявления, не замеры.
3. **Физика** (`ROOFLINE.md`, PROVISIONAL): при batch=1 конвейер по слоям ограничен полосой одной карты; у GLM-5.3-Flash 8.3B
   неэкспертных активных параметров читаются каждый токен (8.2 GiB при Q8_0) — **≤ ~40 tok/s в конвейере при любом попадании в кэш**;
   50+ требует деления плотной части между картами (TP/аналог) или спекуляции. Модель, целиком помещающаяся в VRAM, снимает
   RAM/NVMe-члены. Полное внимание на 262K читает гигабайты KV на токен (MiMo ≈ 5.6 GiB при f16).
4. **Исследования** (`research/R1…R4`): на индексе Artificial Analysis v4.3 модели, физически помещающиеся в сервер в 4 битах,
   близки по качеству (REPORTED: GLM-5.3-Flash 42, Qwen3.8-Flash-Next 40, DeepSeek-V4.1-Flash 39, MiMo-V2.6-Flash 38).
   **Qwen3.8-Flash-Next** (125B + 51B n-gram, 6B активных, 262K нативно, разреженное+линейное внимание) — единственный сильный
   кандидат, целиком помещающийся в 120 GB VRAM в UD-Q4_K_XL (111.3 GB вместе с n-gram-таблицей, которая живёт в RAM); для неё
   уже есть зрелый движок (Strata upstream @fb58e0d) и замеры сообщества на похожем железе: **61.5 / 72.1 / 70.2 tok/s при
   2.7K / 64K / 128K на одной 32 GB карте + AVX2 Threadripper** (REPORTED, `bench/results/2026-10-01-community-rtx-pro-4500`).
   На штатном драйвере GeForce P2P выключен (REPORTED/VERIFIED по чужим замерам, R4); vLLM на >2 PCIe-GPU без NVLink отключает свой
   all-reduce (VERIFIED по коду, R3).
5. **Движки** (`research/R2-engines.md`, проверено ведущим): в llama.cpp с 2026-10-07 есть GPU-кэш экспертов, лежащих в RAM
   (`--moe-cache-mib`, коммит `d6cf9acb2`, политика **LRU с копированием по PCIe при промахе** — `src/llama-moe-cache.cpp:15,72`),
   с 2026-10-08 — на нескольких GPU (`c811cb8f0`); тензорного параллелизма для `glm5-next` нет ни в llama.cpp, ни в ik_llama (R2,
   VERIFIED там); ExLlamaV3 v1.6.0 заявляет TP/EP без NCCL и P2P и поддержку GLM5-Next/MiMo-V2/DeepSeek-V4 (R2); путь DSA-индексера
   в vLLM требует DeepGEMM (только Hopper/Blackwell) → GLM-5.3-Flash в vLLM на sm_89, вероятно, не запустится (HYPOTHESIS, R2);
   апстрим Strata ушёл от нашего пина на 1552 коммита (CONFIRMED: `git rev-list --count c499bd1..fb58e0d`) и остаётся однопородным
   (только Qwen3.8-Flash-Next). Прогноз R2 для GLM-5.3-Flash ≥4 бит на этом сервере без спекуляции — 20–40 tok/s (HYPOTHESIS);
   реальные чужие замеры GLM в 4 битах на 3090-классе с выгрузкой — 6–20 tok/s (REPORTED).

## Решение

**D1. Цели и критерии приёмки** — требования заказчика (п. 1 контекста) становятся сквозными критериями всех гейтов. «Флаг
`--ctx-size 262144`» не является PASS: нужны пробы качества на полной длине (`tools/bench/probes.py`) и декод, измеренный при
заполненном контексте (`tools/bench/run_matrix.py`).

**D2. Модель — по Pareto «качество ↔ скорость ↔ контекст ↔ надёжность», шорт-лист для первых замеров (порядок = порядок запуска):**
1. **Qwen3.8-Flash-Next, UD-Q4_K_XL** — главный кандидат по скорости при 262K (всё в VRAM). Блокер: условия Qwen Community License
   для сценария заказчика (REPORTED: для «AI work assistant»/MaaS третьим лицам нужна отдельная лицензия) — **решает заказчик**.
   Риск движка: setup Strata рекомендует для split UD-Q4_K_XL RAM ≥ ~135 GB (арена экспертов в RAM), у сервера 128 GB; по коду
   установщика это не запрет («128 GB ran it fine», #737, REPORTED) — проверить при запуске (`BRINGUP-qwen38fn.md`).
2. **GLM-5.3-Flash, UD-Q4_K_XL** (MIT) — главный кандидат по качеству среди помещающихся; требует VRAM+RAM и (для 50+) TP/спекуляции.
3. **DeepSeek-V4-Flash-0731, UD-Q4_K_XL** (MIT) — родные FP4-эксперты без потерь, ~82% экспертов в VRAM (PROVISIONAL).
4. **MiMo-V2.6-Flash-MOPD, MXFP4** (MIT) — родной 4-бит; на 262K дорогое полное внимание.
Вне шорт-листа скорости: DeepSeek-V4.1-Flash (в 4 битах не помещается в VRAM+RAM → NVMe в активном пути, ≤ ~16 tok/s) — только
эталон качества. Выбор фиксируется отдельным ADR по итогам R2 (качество на задачах заказчика в 4 битах + скорость на 262K).

**D3. Движок — направление A (готовые движки без форка) как база, своё — только по измеренному разрыву:**
- Бейзлайны R1: Strata upstream (для Qwen3.8-Flash-Next), llama.cpp mainline и ik_llama.cpp (все GGUF-кандидаты; режимы `-sm layer`,
  `-sm row`, `-sm tensor`/`-sm graph` где есть; эксперты в RAM через `-ot`/`--n-cpu-moe`; `--moe-cache-mib`), ExLlamaV3 (TP/EP без
  P2P — проверить заявление; ExLlamaV3 — MIT, а его сервер TabbyAPI — AGPL-3.0: без модификации и раздачи — допустимо, R2), vLLM/SGLang — только для конфигураций, целиком помещающихся в VRAM и поддерживаемых на sm_89,
  с замером цены all-reduce без P2P.
- Первый кандидат для D: политика llama.cpp `--moe-cache-mib` (сейчас LRU + копия по PCIe при промахе) против профиля/TinyLFU и
  счёта промахов на CPU — сначала на трассах (`tools/g0/cachesim.py`), затем патчем в `patches/llama.cpp/` с бенчмарком до/после.
- Своя разработка ограничивается тем, чего нет в готовых движках и что даёт измеримый выигрыш: инструменты замеров (готовы:
  roofline, трассы маршрутизации, симулятор кэша, стенд бенчмарков), эксплуатационный слой (API-шлюз, кэш префиксов/снимки состояния
  на NVMe, наблюдаемость, health/restart, доступ), затем при необходимости — **D: собственный планировщик размещения экспертов и
  TP плотной части поверх выбранного рантайма** (через патчи в `patches/<engine>/`).
- **E (новый рантайм) не начинается**, пока A–D не исчерпаны и roofline не показывает запас ≥ 1.5× над лучшим измеренным движком.

**D4. Старые базы и треки замораживаются** (HISTORICAL, без удаления): база A (strata-glm + патчи 0001–0006), база B (lighttransport),
трек DFlash2, «день GPU». CI-сборки держатся зелёными, новых работ нет. Их дизайн (ярусы, O_DIRECT, разбиение по слоям) —
донор для D. Разморозка — только если R1 покажет, что именно они закрывают разрыв (например, лучший GLM-путь).

**D5. Квантование:** основные веса — 4-бит класс и выше (Q4_K/UD-Q4_K_XL, IQ4_XS, родные MXFP4/FP4, AWQ/GPTQ-INT4); Q2/Q3 — только
как отдельный экспериментальный режим с измеренным штрафом. NVFP4 на sm_89 — только через W4A16-фолбэк, низкий приоритет.
KV: f16 по умолчанию; FP8/Q8 — после эксперимента K2 (накопление внимания в fp32).

**D6. Многокарточность:** базовый режим — конвейер по слоям (не требует P2P). TP/EP — только после замеров H6 (P2P) и P2
(all-reduce). Патч драйвера для P2P на GeForce (tinygrad/aikitoria) — **опциональный эксперимент с явного согласия заказчика**
(изменение системного драйвера, риски — R4 §4.2).

**D7. Ярусы памяти:** VRAM — активные веса и KV; промахи мимо VRAM считает CPU из RAM (а не копирует по PCIe) при batch=1;
NVMe — холодные данные: файлы моделей, снимки KV/состояния для кэша префиксов, n-gram/Engram-таблицы, профили маршрутизации;
**в активном пути экспертов NVMe не используется** для целей 50+ tok/s. Все 4 NVMe используются для независимых файлов
(модели, снимки, таблицы) и параллельного чтения; RAID0 vs шардинг — по замеру H7/P3.

**D8. Длинный контекст и повторные агентные запросы:** кэш префиксов и сохранение/восстановление состояния (KV + рекуррентные
состояния) — обязательная часть платформы (TTFT префилла 262K — минуты; восстановление — секунды, PROVISIONAL).

## Рассмотренные альтернативы

| # | альтернатива | почему не выбрана сейчас | что вернёт её |
|---|---|---|---|
| A1 | продолжить старый план: GLM на базе B, сначала Q2 | Q2 нарушает ≥4-бит; parity не доказан автором; один GPU; нет кэша префиксов/батчинга | — |
| A2 | GLM на базе A (strata-glm, NVFP4) | архивный однопородный движок; FP4 на sm_89 программно; нет сервера; все наши запуски — синтетика | R1 покажет, что база A — лучший GLM-путь на 4 картах |
| A3 | сразу писать свой рантайм (E) | нет ни одного замера; готовые движки, возможно, уже достигают целей для Qwen3.8-Flash-Next | A–D не достигают целей при запасе roofline ≥ 1.5× |
| A4 | только vLLM/SGLang TP=4 | только для моделей целиком в VRAM; без P2P all-reduce через NCCL/хост; MoE на batch=1 выигрывает от TP мало (R3: gpt-oss ×1.00) | H6/P2: P2P работает и all-reduce ≤ 30 мкс |
| A5 | DeepSeek-V4.1-Flash с NVMe-ярусом как основная модель | NVMe в активном пути: ≤ ~16 tok/s в 4 битах | заказчик ставит качество выше скорости |
| A6 | (выбрано) измерения → готовые движки → свой слой D | — | — |

## Цена ошибки и откат
- Если Qwen3.8-Flash-Next не проходит по лицензии или качеству — шорт-лист сдвигается на GLM/DeepSeek-V4-Flash без потери работы:
  инструменты и стенд модель-агностичны.
- Если готовые движки на 4×4080 окажутся сильно ниже границ roofline (< 50% вместо ~70% калибровки) — это сигнал к D/E, а не к
  понижению битности.
- Откат решения: вернуть статус ADR-007/009/010 из `docs/DECISIONS.md` (там ничего не удалено), разморозить треки.

## Что решает заказчик (не инженерные вопросы)
1. Допустима ли Qwen Community License 1.0 для его сценария использования (юридический вопрос).
2. Согласие на установку модифицированного драйвера NVIDIA для P2P (опционально, после замеров).
3. Окна простоя для BIOS-шагов и (если это хост Proxmox) перезагрузок.
